```

```

In the AI chat: `Load <kit_ref>/requirements/prompt.md.` → `REQUIREMENTS: <name> — <what you
want>`, then `PLAN:` → `IMPLEMENT:` → `PR:` (below). New version of the kit:
`git submodule update --remote <kit_ref>`, then commit.

Generated by spec-nx `<spec_nx_version>` with `<model>` on `<generated>`. Do not edit the files
in this folder by hand: `GENERATE KIT --update` replaces them. Project rules go into
`.specs/guidelines/`; the project's specs into `.specs/features/`.

## How to use a stage

In the AI chat of your editor, load the stage prompt and type its command:

```
Load <kit_ref>/<stage>/prompt.md.
<COMMAND>: <arguments>
```

## The workflow

One feature = one spec = one branch `feature/<name>` = one pull request. Every commit message
carries the reference of the spec's issue (`#<n>`) or backlog item (`AB#<id>`) —
`guidelines/commits.md`.

| # | Stage | Command | Result |
|---|-------|---------|--------|
| 1 | requirements | `REQUIREMENTS: <name> — <what you want>` | Part 1 of `.specs/features/<date>_<name>_spec.md`; answer its open questions with `REQUIREMENTS: <spec file> — <answers>` |
| 2 | plan | `PLAN: <spec file>` | Part 2: Steps, decisions, Definition of Done |
| 3 | implementation | `IMPLEMENT: <spec file>` — once per Step, commit after each | Code + the Step marked done |
| 4 | documentation | `DOCS: <spec file>` | The documents the change affects |
| 5 | review | `REVIEW: <spec file>`, `CODE REVIEW: <spec file>` | Semantic diff for the pull request; findings in the Review Log |
| 6 | implementation | `CLOSE: <spec file>` | Spec moved to `.specs/features/done/` |
| 7 | pr | `PR: <spec file>` | Pull request (and issue) updated with the spec summary |

## Models and cost

- **Models** (`models.md`): <per Step — reasoning <model>, standard <model>, light <model> /
  fixed <model>>. Each stage checks its model first and runs as a sub-agent on it where the
  tool allows; the plan gives every Step a tier; `IMPLEMENT:` asks once and runs the Steps on
  their models. Change it in `.specs/spec-nx.json` (`models`), or only for you in
  `.specs/spec-nx.local.json` (`null` = always your tool's model).
- **Tokens and cost** (`COSTS.md`): every Stage log row and Done line gets its tokens and cost
  in <currency>; `CLOSE:` adds a cost summary and rebuilds `.specs/costs.md`. **All costs are
  estimates and may be wrong.** Turn it off with `"enabled": false` in the `cost` block.

## Now and then

| Command | Stage | Does |
|---------|-------|------|
| `CREATE ISSUE: <spec file> [parent <n>]` | requirements | Creates the issue / backlog item of the spec (optionally under a parent); offered when the requirements are finished |
| `UPDATE ISSUE: <spec file>` | requirements | Summary of the spec into its issue / backlog item |
| `GUIDELINES: <language>` | guidelines | Writes or updates `.specs/guidelines/<language>.md` |

## Settings

**You can customize the kit per project and per developer.** Three files, each winning over
the one before:

1. the kit's `<kit_ref>/.specs/spec-nx.json` — only when the kit is a repository of its own
   (a submodule): its defaults for every project that uses it;
2. `.specs/spec-nx.json` — the project's (committed);
3. `.specs/spec-nx.local.json` — yours (not committed).

A file holds only what it changes. A key replaces the same key; objects (`work_items`,
`cost`, `models`) are merged key by key; lists (`stages`) are replaced as a whole; `null`
removes the key. `version`, `spec_nx_version`, `generated`, `kit`, `kit_dir`, `kit_ref`,
`kit_files`, `shells` (and `model` of a shared kit) come from the project's file only.
`<kit_ref>/tools/settings.ps1` / `settings.sh` show every setting with the file it comes from.

When the settings list `stages`, each stage runs only when it is in it (or in `on_demand`) — with
`"stages": ["requirements"]` in your file, the other stages say they are turned off for you —
and its report names the settings it used that do not come from the kit. `GUIDELINES:` is
always part of the kit and is never turned off. All keys and
examples: [Customizing spec-nx](https://github.com/martinnordio/spec-nx/blob/main/docs/customize.md).

## Prompt log

Off by default. With `"prompt_log": true` in your settings (usually your own
`.specs/spec-nx.local.json`), every stage that runs adds the prompt it was given — the
command and its text as the user typed them, without `Load …` lines — at its start, and fills
in its reply summary when it ends:

- `.specs/prompts/<yyyy_mm_dd>_<name>_prompt.md` — the prompts of the spec
  `<yyyy_mm_dd>_<name>_spec.md`; the first `REQUIREMENTS:` uses the name the spec is about to
  get;
- `.specs/prompts/<yyyy_mm_dd>_other_prompt.md` — the day's prompts that belong to no spec
  (for example `GUIDELINES:`, `GENERATE KIT`).

A new file starts with `# Prompt history`, one sentence about what it holds (the spec, or "the
prompts of <date> that belong to no spec") and `---`. Prompts are numbered per file. Each
prompt:

```markdown
## Prompt <n> — <short title>

<yyyy-mm-dd> · `<COMMAND:>` · <model>

> <the prompt, exactly as given, every line quoted>

Reply summary: <two or three sentences: what was done or decided>

---
```

A stage that stops early writes why in its reply summary; a stage that is turned off writes nothing.

Passwords, tokens and keys are written as `«redacted»`. The files are committed with the
spec; to keep them private, add `.specs/prompts/` to your `.git/info/exclude`. With the log
off, nothing in `.specs/prompts/` is created or changed.
